# تجاوز NumberOfNames: نتائج جديدة

**لم يظهر خلل عام في Wine مرتبط بالتجاوز يمكن ترقيعه. أثبت القياس الجديد أن حقل العدد الصحيح بقي1468، ولم يُعَد الوصول إليه من خيط التهيئة أثناء المسح، وأن الواجهات العامة المرصودة لم تكشف اسم هدف Adhesive. السبب الذي يسمح لفرع الاستمرار بتجاوز الحد ما زال غير محدد؛ بياناته المطلوبة أدناه.**

## اختلاف البنية: فرضية علامة نهاية خاصة بـWindows مرفوضة

أعدنا استخدام metadata الأصلية من Windows Server2022/NTDLL10.0.20348.5622، وملف Wine11.0 ذي البصمة المطابقة للتحقيق السابق. لا تنزيل DLL من Windows ولا تشغيل TLS أو إعادة اختبار جميع الصادرات.

| الخاصية | Wine | Windows المرجعي |
| --- | ---: | ---: |
| أسماء / خانات وظائف | 1468 /1468 | 2457 /2458 |
| Ordinal Base | 1 | 8 |
| نهاية جدول الأسماء | `CCE08` | `15FB44` |
| بداية جدول ordinals | `CCE08` | `15FB44` |
| أول DWORD بعد الأسماء، معاد بناؤه من metadata الـordinals | `10000` | `20001` |

**الجدولان متجاوران دون NULL sentinel في المرجعين.** التجاور الذي يجعل القراءة الخارجة تصل إلى ordinals ليس عيبًا خاصًا بـWine. صيغة [Microsoft PE](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#export-name-pointer-table) تحدد عدد عناصر جدول الأسماء؛ لا تعتمد نهاية المسح على sentinel. هذه نتيجة بنيوية جديدة، وليست ادعاء أن Adhesive تعتمد sentinel فعلًا.

1468اسمًا في Wine سليمة في الحقول المفحوصة، دون تكرار، ومرتبة ASCII، ومؤشرات ordinals ضمن مجال الوظائف. الأسماء المشتركة1408 بترتيب نسبي متطابق؛ هناك1049اسمًا في Windows غائبة من Wine و60بالعكس. هذه فروق تغطية مؤكدة، **ولا تسمّي وحدها API التي تحتاجها هذه التهيئة**. اشتراك اسمين في RVA واحد بالمرجع لا يثبت تكافؤ تنفيذهما أو يبرر إنشاء alias في Wine. التفاصيل في `export-contract.json`؛ مصدر المرجع الأصلي وCI42088585400 محفوظان في Index-Origin.

## اختبار مستقل جديد لمسار الاسم غير الموجود

بُني `resolver-fixture.exe` دون FiveM أو Adhesive أو Static TLS. نجحت **8تحققات** على Wine: اسم موجود، اسم تحكم غائب، اختلاف حالة الأحرف، اتفاق Win32 مع واجهة NT، وفشل الأخيرة بـ`C000007A`. GetProcAddress أعاد NULL وerror127 للاسم الغائب. هذه نتائج متفقة مع [عقد Microsoft العام](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress) بشأن الغياب وحالة الأحرف؛ **لم نشغّل عينة جديدة على Windows في هذه المرحلة**. حالة NT مرجعها تنفيذ Wine المفتوح، وليست قياسًا جديدًا لنظام Windows.

في [Wine11.0 loader.c](https://github.com/wine-mirror/wine/blob/wine-11.0/dlls/ntdll/loader.c)، البحث العام يحد المجال بـNumberOfNames ويتعامل مع not-found؛ ليس هذا المسار العام هو الحلقة الواقعة داخل Adhesive. لا يثبت الاختبار سلامة كل API أو هوية الهدف المجهول.

## القياس الجديد داخل FiveM

بُني observer ظاهر بنقاط توقف عتادية، دون كتابة كود/ذاكرة الطفل أو تغيير قيم إرجاعه. اجتاز العينة المستقلة: **10أزواج دخول/عودة** للواجهتين، و**4قراءات مراقبة** لعدد تحكم، بلا خطأ. عدد التحكم متغير من برنامجنا للتحقق من debugger؛ ليس محاكاة لـWindows أو مرجعًا لسلوكه.

التشغيل المعتمد `private/fullhost-fault-audit` على Wine الأصلي، بالشبكة معطلة وprefix التشخيص السابق فقط. القياس يخص خيط التهيئة المرصود، من أول lookup بفهرس0 إلى أول AV. لم يُعد اختبار TLS أو تغيير Wine أو FiveM.

| القياس الجديد | النتيجة |
| --- | --- |
| العدد عند أول lookup ثم عند AV | **1468 في الحالتين** |
| النسخة المستخدمة عند أول lookup وعند AV | نفس buffer |
| إعادة الوصول إلى حقل NumberOfNames المراقَب أثناء المسح | **0** |
| DR3 وعرض/نوع المراقبة عند AV | العنوان نفسه، read/write بطول4بايت، مفعلة |
| طلبات حلّ NTDLL عبر الواجهتين أثناء المسح | **0** |
| أزواج الواجهات قبل AV | 39عند NT و32عند Win32؛ الطبقتان قد تخصان الطلب نفسه |
| مستدعٍ ظاهر داخل Adhesive لهذه الطلبات | 0 |
| حالة الانهيار | index1477، name RVA=`130012`، fault=`D9FEC5`، ثم998 |
| أخطاء المراقبة | 0 |

الواجهتان هما `kernel32!GetProcAddress` و`ntdll!LdrGetProcedureAddress`. تسمية initiator تعني المستدعي الظاهر تحت wrapper المتتبع؛ **ليست فكًا كاملًا للمكدس أو إثباتًا لتغطية جميع الخيوط والـresolvers الخاصة**.

الفشل الوحيد قبل AV كان طلبَي CoreRT لـ`ZwQueryDebugFilterState`، ويظهران في الطبقتين. مصدرهما مسار HardErrorScope السابق؛ لم نعد تجاربه ولم نعتبر ظهورهما سببًا جديدًا أو نغيّر API أمنية/تشخيصية لفرض نجاحها.

## ما الذي حُسم وما الذي بقي؟

**حُسم:** لا دليل على تلف العدد في النسخة المستخدمة، أو علامة نهاية خاصة يوفرها Windows ويفقدها Wine، أو فشل مرصود للـresolver العام أثناء الحلقة يحدد اسم API ناقصة. استمرار iterator داخل المكتبة هو موضع مخالفة حد PE المثبت سابقًا؛ بقيت نتيجته نفسها دون تعديل.

**لم يُحسم:** قد يكون العدد أو حد آخر قد حُفظ قبل lookup0؛ غياب قراءته لاحقًا لا يثبت غياب مقارنة بحد محفوظ. كما لا تميّز هذه الأدلة بين هدف عام غائب بالفعل، أو مدخل بحث غير صحيح، أو افتراض خاص داخل initializer بشأن العثور على الهدف. جميعها قد تعطي التسلسل المرصود نفسه. لا نسمي سببًا جذريًا نهائيًا من هذا القياس.

المعلومة الحاسمة المطلوبة من Cfx.re هي **هوية Windows export المقصود، والحد الفعلي/شرط not-found عند الانتقال1467→1468 ومصدر قيمته المحفوظة**. يمكن لتشخيص معتمد إخراج الاسم والحد فقط دون كشف خوارزمية حماية أو تغيير قرارها. المسودة الدقيقة في `CFX_REQUEST.md`، ولم تُرسل. لا نحتاج PDB كاملًا أو dump كاملًا لهذا الطلب.

## المحاولات غير المعتمدة والحفظ

محاولتا `fullhost-public-resolver-and-bound` و`fullhost-progress` لم تكملا القياس؛ حدد السجل الثاني الوقوف داخل GetThreadContext لخيط آخر أثناء حدث تحميل DLL. محاولة `fullhost-event-thread` أتمت أداة المراقبة دون بلوغ Adhesive خلال حدها؛ لا تُحسب قياسًا للحلقة. اقتصر الإصدار اللاحق على الخيط الرئيسي، واجتاز التحكم ثم أتم `fullhost-primary-only` وأُضيف إليه تدقيق سجلات AV في `fullhost-fault-audit`. هذه إصلاحات لأداة التحقيق، **وليست أخطاء Wine عامة مثبتة أو إصلاحات لتشغيل Adhesive**.

كل النتائج والأصول السابقة محفوظة. لا patch لـWine أو FiveM أو Adhesive في هذه المرحلة. البصمات وحالة المصدر والاستعادة في `preservation.json`. الملفات التنفيذية الجديدة أدوات قياس فقط. إعادة التحقق والأوامر في `RETEST.md`.
