# لماذا يختلف الفهرس؟ نتيجة المقارنة الجديدة

**ثبت اختلاف مجموعات الصادرات ومواضع الأسماء، ولم يثبت بعد سبب اختيار Adhesive للفهرس1477 أو خلل Windows API عام في Wine. لا يوجد patch مبرر حاليًا.**

## ما نُفذ

1. تأكدنا أولًا من إغلاق Ghidra وغياب ملفَي القفل والعملية النشطة. فُتح المشروع الموجود بـ`-readOnly -noanalysis`؛ بصمة البرنامج المحفوظ تطابق Adhesive الرسمي. لم نعد Auto Analysis أو نصدر المكتبة أو ننسخ قاعدة البيانات.
2. استُخدم Windows أصلي متاح عبر مستودع CI المصرح به. شُغّل برنامج Python مستقل يجمع **بيانات جدول exports فقط** ويقارن العناوين بنتائج GetProcAddress داخل عملية الاختبار. لم يُرفع Adhesive أو سجل محلي، ولم يُنزّل ملف Windows DLL.
3. جُمعت بنية جدول ملف Wine الموجود محليًا دون تشغيل FiveM أو إعادة اختبارات Imports/I/O/HardErrorScope. جرت المقارنة بواسطة `compare_exports.py`.

## مرجع Windows وحدوده

[CI ناجح42088585400](https://github.com/feraskozx1-byte/fivem-pr4050-build/actions/runs/42088585400)، commit `a242850969b97982228f9211bacf53ae74bf8d8e`، فرع مستقل `codex/ntdll-export-reference-20261105`. لم يُشغّل بناء FiveM.

المرجع **Windows Server2022 x64**، NTDLL `10.0.20348.5622`، runner image `20261101.353.1`. نطاقه عقد PE/GetProcAddress؛ توافقه كعميل FiveM لم يُختبر أو يؤكده Cfx.re. لا نعتبره نسخة Windows مطابقة للبيئة التي بُنيت عليها Adhesive.

`RtlSetSecurityObjectEx` غير موجود في جدول Wine المرصود. لكن وجوده عند1477 في هذا المرجع **لا يثبت أن Adhesive تبحث عنه**. لا نستنتج وظيفة مقصودة أو نكتب تنفيذًا تخمينيًا من تطابق رقم واحد مع نسخة Windows واحدة.

في Windows، تطابقت جميع2457صادرات مسماة مباشرة مع GetProcAddress: صفر اختلاف. نتائج RCA السابقة على Wine أثبتت اتساق1468صادراته مع الواجهة نفسها؛ لم نكرر اختبارها. المقارنة تفحص **حل العناوين**، ولا تختبر تنفيذ كل وظيفة أو خصائص الحماية.

صيغة PE تفصل name index عن ordinal، وتحدد حجم جدول الأسماء بعدده؛ لا تعطي الاسم موضعًا مطلقًا موحدًا بين DLLs مختلفة. اختلاف العدد وOrdinal Base بذاته لا يخالف البنية. [Microsoft PE](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#export-name-pointer-table)، و[GetProcAddress](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress).

## ماذا كشف Ghidra عن منتج1477؟

التحليل المحفوظ لا يعرّف دالة تحتوي lookup عند `D9FDE7`. سجل unwind يحدد النطاق `D9DF40..DA602D` بحجم33006بايت، لكن تعريف الدالة المحفوظ عند بدايته يغطي193بايتًا فقط. قراءته المحدودة نجحت:65عملية SSA، دون مسار مستعاد يصل إلى lookup. المقطع ينتهي بقفزة محسوبة عند `D9DFFF`؛ التحليل المحفوظ لا يحل وجهتها إلى الكتلة المعنية.

لم نحذف تعريفات المشروع أو نفرض حواف تحكم مختلقة. الجلسة كانت read-only والمعاملة أُلغيت صراحة؛ لا تغييرات محفوظة. التفاصيل في `private/index-fragments-v3.txt`. هذه **حدود التحليل الساكن المنفذ**، وليست برهانًا أن استرجاع المسار مستحيل. أخطاء تشغيل سكربت التشخيص السابقة محفوظة منفصلة، ولا تُحسب نتائج للمكتبة.

## الفصل بين الفرضيات

| الفرضية | الدليل الحالي | المعلومة الحاسمة الناقصة |
| --- | --- | --- |
| استخدام index/hint/ordinal مشتق من جدول Windows مختلف | اختلاف المواضع مثبت؛1477 صالح في المرجع وخارج Wine | مصدر1477 ونوعه وعقد المستدعي |
| البحث عن export غير موجود ثم تجاوز حد الجدول | اختلاف تغطية الصادرات مثبت | هوية الاسم المطلوب ومسار عدم العثور عليه |
| مخالفة عامة في GetProcAddress أو بنية PE | لم تُرصد في القياسات المحددة | عملية API مرتبطة بمنتج1477 تخالف عقدًا موثقًا |

**ما لا يجوز استنتاجه:** أن كل export ناقص مطلوب لهذا initializer، أو أن1477 رقم ثابت في Adhesive، أو أن ترتيب Windows المرجعي هو ترتيب Windows المستهدف، أو أن زيادة عدد exports ستحل التهيئة. لا نضيف أسماء وهمية ولا نعيد ترتيب الجدول لفرض نجاح lookup.

## القرار والخطوة التالية

الأدلة الحالية تبرر طلب **تفسير منتج الفهرس من مطوري Adhesive**، ولا تبرر تعديل Wine. البيان المطلوب تحديدًا عند المدخل السابق لـ`D9FDEE`: هل القيمة name index أو hint أو ordinal؟ ما هو Windows export المقصود؟ من أي جدول/نسخة وحجم اشتُقت1477، وما نتيجة مسار البحث عند عدم وجود الاسم؟

يمكن لـCfx.re توفير diagnostic build يخرج هذه البيانات دون تغيير القرارات الأمنية. عند معرفة اسم API المطلوبة يمكن فحص تنفيذها العام في Wine وبناء reproducer مرتبط بها. لم نثبت أنها RtlSetSecurityObjectEx، ولم ننشئ patch أو ندّع نجاح تشغيل Adhesive. مسودة المتابعة في `CFX_FOLLOWUP.md`، لم تُرسل.

## الأدلة وإعادة التحقق

- `ntdll-wine.json`: بيانات الملف المحلي وبصمته.
- `windows-reference/ntdll-windows-reference.json`: بيانات المرجع واختبارات GetProcAddress، دون DLL bytes أو عناوين وظائف مطلقة.
- `comparison.json`: الفروق المحسوبة والأسماء العامة المختلفة.
- `ci-reference.json`: المصدر والـcommit والملفات المرفوعة؛ `preservation.json`: التحقق النهائي.

```bash
# مقارنة الأدلة المحفوظة؛ لا تشغّل FiveM:
python3 Diagnostics/2026-11-05-Adhesive-RCA/Index-Origin/compare_exports.py

# لقطة جديدة من ملف Wine إلى مسار ناتج غير موجود:
python3 Diagnostics/2026-11-05-Adhesive-RCA/Index-Origin/collect_ntdll.py \
  --file Diagnostics/2026-11-05-Compatibility/private/api-probe-cachyos/prefix/drive_c/windows/system32/ntdll.dll \
  --output /tmp/ntdll-wine-new-reference.json
```

كل النتائج الجديدة داخل هذا المجلد. لم تتغير ملفات تشغيل FiveM أو المكتبة الرسمية أو إعدادات prefix. لا يوجد DLL تجريبي لاعتماده أو تراجع عن patch؛ فرع CI منفصل ويحتوي إضافة برنامج عام ووصفة القياس فقط.
