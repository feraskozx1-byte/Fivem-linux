# RCA: تفسير مصدر القراءة غير الصالحة

**تقدم مثبت، وليس إصلاح تشغيل:** أثبتنا أن `0x130012` يأتي من تجاوز جدول أسماء exports في نسخة NTDLL. لم نثبت بعد لماذا أُنتج الفهرس `1477`. لذلك لا نعلن اكتمال السبب الجذري، ولا ننسبه إلى Wine دون دليل.

## الدليل الجديد

بُنيت أداة Windows Debug API محلية، وشغّلت FiveM الحقيقي في تخطيط Phase2 التشخيصي الموجود، بالشبكة معطلة. لا breakpoints برمجية أو كتابة ذاكرة أو تعديل context أو تزوير نتائج. المصحح ظاهر للعملية؛ أُعيد الاستثناء `DBG_EXCEPTION_NOT_HANDLED` ليعالجه المحمّل طبيعيًا. التُقطت عينات صغيرة قبل فك المكدس، ولم تُرفع.

| القياس | النتيجة |
| --- | --- |
| الفهرس المستخدم، ESI وstack+0x40 | `1477 = 0x5C5` |
| NumberOfNames وNumberOfFunctions | كلاهما `1468 = 0x5BC` |
| stack+0x20 | يطابق r9، قاعدة نسخة NTDLL |
| stack+0x30 | `0xCA000`، RVA دليل exports |
| AddressOfNames | `0xCB718` |
| AddressOfNameOrdinals | `0xCCE08` |
| lookup الفعلي | `0xCB718 + 4*1477 = 0xCCE2C` |
| DWORD المقروء من العينة داخل العملية | `0x00130012`، زوج ordinals رقمَي 18 و19 |
| القراءة التالية | `r9 + 0x130012` عند Adhesive+`D9FEC5` |
| حالة الهدف عند أول استثناء | `MEM_RESERVE=0x2000`، Protect=0؛ ليست MEM_FREE |

الحساب يفسر سلسلة الفشل:

```text
نهاية جدول الأسماء = 0xCB718 + 4*1468 = 0xCCE08
lookup[1477]       = بداية جدول ordinals + 36 بايتًا
DWORD             = 18 | (19 << 16) = 0x130012
قراءة اسم مفترض    = base + 0x130012، خارج SizeOfImage=0xD8000
```

القراءة المحدودة للتعليمات أثبتت تمرير هذا المدخل: RVA `D9FDDF` يقرأ حقل AddressOfNames، و`D9FDE7` يأخذ ESI كفهرس، و`D9FDEE` يقرأ DWORD من جدول الأسماء. لا استدعاء أو تعديل RAX بين هذا التحميل وقراءة البايت عند `D9FEC5`. لم نحلل أو نغير قرارًا أمنيًا.

هذه قراءة 32-bit صحيحة النوع **لجدول أسماء**، لكنها تجاوزت حدوده إلى جدول ordinals ذي العناصر 16-bit؛ لا يثبت ذلك وجود خطأ ABI بعرض الأنواع. [مرجع Microsoft لبنية PE](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#export-name-pointer-table).

## ضوابط المقارنة والاختبار

- لقطة الترويسة للـbuffer تطابق أول1024بايت من ملف NTDLL. ترويسة النسخة المحملة تطابقه أيضًا بعد أخذ تحديث ImageBase إلى عنوان التحميل الفعلي في الحسبان. دليل exports وآخر جدول الأسماء وأول ordinals متطابقة بايتًا ببايت في النسختين والملف. لا دليل هنا على جدول NTDLL مختلف أو تالف في الذاكرة.
- تطابق RVA وRAX وRSI وسلسلة initializer مع Direct-Repair **دون debugger**. لذلك ليست هذه أول مشاهدة للفهرس الخاطئ بسبب المصحح. الحالتان الجديدتان عادتا إلى فشل تحميل Adhesive؛ لا ادعاء بتشغيل الحماية.
- `export-probe.exe` مستقل، لا يحمل FiveM أو Adhesive. فحص1468اسمًا وordinal/RVA، وقارن جميع العناوين مع GetProcAddress: **10تحققات، صفر فشل، صفر اختلاف resolver**. أعاد حساب `0x130012` من الفهرس المرصود ورفض تفسيره كـRVA صالح دون محاولة قراءته. هذا يعيد إنتاج الحساب الخاطئ، **ولا يعيد إنتاج اختيار1477 داخل Adhesive**.
- لا Windows مرجعيًا شُغّل في هذه المرحلة. المقارنة البنيوية تستند إلى صيغة PE الموثقة، وليست ادعاء باختبار تفاضلي على Windows.

الأدلة القابلة لإعادة التحقق: `evidence.json`، `exception-excerpt.txt`، و`private/export-table-provenance/rca-debug-result.txt` والعينات المشار إليها في `analyze-rca.py`. نتائج الاختبار المستقل: `private/export-contract/results.txt`.

## ما تغيّر في التشخيص

خطأ998 نتيجة ثانوية لفشل PROCESS_ATTACH بعد الاستثناء. UCRT يظهر كمستدعٍ للـinitializer؛ وجوده بالمكدس لا يثبت خلل CRT. كما لا تبرر اللقطة زيادة تخصيص الذاكرة أو جعل صفحات إضافية committed: الـRVA نفسه جاء من تفسير بيانات جدول مجاور كاسم.

موقع `0x130012` داخل COFF string table على القرص كان ملاحظة أولية؛ مصدر القيمة المثبت الآن هو جدول ordinals، فلا نعتمد مصادفة موقع COFF تفسيرًا. لم نكرر تجارب HardErrorScope أو Imports أو I/O السابقة.

المتبقي هو **منتج الفهرس**: هل1477 ناتج عن افتراض خاص بإصدار Windows، أو مسار بحث لم يجد export، أو خطأ سابق في تمرير مدخلات البحث؟ لا دليل كافيًا للاختيار بينها أو لتأكيد توافق ABI الخاص بالمكتبة. محاولة SSA محدودة على مشروع Ghidra المحفوظ أُجهضت بسبب قفل المشروع المفتوح؛ لم نتجاوز القفل أو نعد التحليل أو ننسخ قاعدة البيانات. السكربت `LookupIndexOrigin.java` وسجل المحاولة محفوظان.

## الإصلاح والبيان المطلوب

**لم نعدل Wine أو FiveM أو Adhesive:** لم يظهر خلل عام مثبت يبرر patch. اختفاء AV بتوسيع الذاكرة أو تجاوز lookup لن يثبت عمل الحماية.

المطلوب المحدد من Cfx.re: تشخيص معتمد عند منتج index السابق لـ`D9FDEE`، يذكر **هوية Windows export المقصود، ومصدر1477، والجدول/العدد الذي يفترضه المستدعي**. معرفة اسم الوظيفة العامة ستتيح فصل export ناقص يمكن تنفيذه في Wine عن افتراض index/سلوك خاص يحتاج إصلاحًا رسميًا داخل المكتبة. المسودة المنقحة القابلة للإرسال في `CFX_REPORT.md`؛ لم تُرسل.
