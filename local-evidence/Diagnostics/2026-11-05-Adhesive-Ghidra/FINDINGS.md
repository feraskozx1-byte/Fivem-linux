# نتائج تدقيق الاستيرادات — دون إعادة تشغيل

**النتيجة B: الأدلة الحالية لا تبرر تعديل Wine.** لا يوجد إصلاح عام مثبت في هذه الجلسة؛ توقفت بعد التدقيق دون إعادة تجارب Phase2 أو تشغيل DLL أو تعديل الحماية.

## الجديد مقارنة بـPhase2

- تأكدت بصمة الملف المطلوب، ثم استُخرجت الاستيرادات بـ`llvm-readobj --coff-imports`: **43 descriptor عاديًا / 634 رمزًا، وdescriptor مؤجل واحد / 3 رموز**؛ الإجمالي637 عبر44 descriptor.
- الجدول المنظم وأسماء الرموز كاملة في [IMPORTS.md](IMPORTS.md)، والنتائج القابلة للتحقق في `imports.json` و`dependency-audit.json`. `audit-imports.py` يقرأ export tables وforwarders دون تنفيذ الملفات. جرى التعامل مع ordinal imports كـordinals، ومع عقود CRT API-set عبر مضيفها UCRT.
- **لا export غائب بين الرموز637** في ملفات بيئة الاختبار الحالية بعد تتبع forwarders. هذا فحص وجود، وليس إثبات تنفيذ الوظائف أو صحة ABI/semantics.
- بالمقارنة مع سجل المضيف الحقيقي السابق، مضيفات الاعتماديات جميعها سجلت PROCESS_ATTACH ناجحًا قبل دخول Adhesive عند السطر19828. وجود ole32 المحمل لا يثبت أن Adhesive استدعى استيراداته المؤجلة قبل العطل.
- لا يوجد descriptor مباشر باسم NTDLL في جدول PE، رغم ثبوت استدعاءات Nt* في relay السابق. لذلك جدول Imports وحده لا يحصر الواجهات المستخدمة ديناميكيًا؛ ظهور اسم في Ghidra ليس بديلًا عن التمييز بين import ثابت وهدف استدعاء أثناء التشغيل.
- ثمانية تحذيرات `No implementation` في PID FiveM تخص استيرادات MSVCP140 من **CoreRT.dll**، لا استيرادات Adhesive المباشرة؛ السطور17121–17128 في `Phase2/private/fullhost-legacy-ui/wine.log`. هذه فجوة معروفة سبق اختبار توفيرها، وليست سببًا جديدًا أو مبررًا لإعادة تجربة CRT. حُفظ الربط في `log-correlation.json`.
- مشروع Ghidra موجود في `/home/feras/FiveM_Compatibility.gpr`، وmetadata البرنامج داخل `.rep/idata/00/00000000.prp` يسمي `adhesive-24769.dll`، مع ملفات قاعدة بيانات محفوظة. لم أفتح قاعدة البيانات الكبيرة أو أعد Auto Analysis؛ وجودها لا يثبت أن أي تعديلات GUI معلقة حُفظت. مقتطف entry المعطى لا يحدد API خاطئة أو مصدر index، ولذلك لم يُفسر منطق التهيئة المغلق.

## إجابات التدقيق

| السؤال | النتيجة المدعومة |
| --- | --- |
| API عامة مطلوبة وغير منفذة؟ | لا نقص جديد مثبت من الاستيرادات المباشرة؛ وجود export لا ينفي stub أو نقصًا دلاليًا. تحذيرات CoreRT الثمانية معروفة سابقًا. |
| نتيجة تخالف Windows الموثق؟ | لا توجد نتيجة مسجلة تثبت ذلك. حالات NTSTATUS الناجحة وحدها لا تكشف محتويات مخرجات APIs. |
| اعتماد عام فشل تحميله وسبب فشل Adhesive؟ | لا يظهر ذلك في مسار التحميل المسجل قبل دخوله؛ المضيفات تهيأت. فشل XAML المنفصل سابق للعطل، وقد فُصل في Phase2. |
| خلل CRT/ABI مستقل قابل لإعادة الإنتاج؟ | لم تُضف الأدلة الحالية واحدًا؛ اكتمال exports لا يصادق على ABI الخاص بالمكتبة المغلقة. |

## قراءة دليل الذاكرة بعقد Windows العامة

لا يصبح الوصول إلى صفحات محجوزة غير committed مشروعًا بمجرد نجاح تخصيص آخر. يفرق [توثيق Microsoft لـVirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc) بين الحجز والـcommit؛ و[مصدر Wine العام](https://github.com/wine-mirror/wine/blob/master/dlls/ntdll/unix/virtual.c#L998-L1027) يبين أن غياب committed bit يمنع منح صلاحيات وصول فعلية. **الاستثناء المسجل متسق مع هذه القاعدة، ولا يثبت أن Wine خالفها.** هذا لا يصادق على allocator كله أو على مطابقة master لنسخة CachyOS.

مطابقة r9 مع malloc وتجاوز حجم الطلب تبقي أصل index وعمر الكائن والحجم الفعلي المتاح مجهولة كما في Phase2. لا نخلط حالة MEM_FREE في العملية الصغيرة مع الرصد الداخلي للمنطقة المحجوزة في المضيف الحقيقي.

**الفجوة المحددة في الدليل العام:** relay سجل عنوان `IO_STATUS_BLOCK` وSTATUS_SUCCESS للقراءتين، ولم يسجل `IO_STATUS_BLOCK.Information` أو محتوى خرج الاستعلام عن الملف. وفق [توثيق NtReadFile](https://learn.microsoft.com/en-us/windows/win32/devnotes/ntreadfile)، Information هو عدد البايتات المقروءة فعليًا، وLength معامل ULONG. لذلك لا يمكن استنتاج مقدار البيانات الصالحة من status أو من بتات معامل سجلها relay كقيمة64-bit. لم يثبت أن هذه الفجوة هي السبب؛ إنها قياس ناقص يمكنه اختبار فرضية I/O عامة دون تفسير الحماية.

لم تُنسخ DLLs، ولم تُعدل ملفات سابقة، ولم تتوفر مقارنة Windows أصلية. لا يوجد أساس لتغيير قيم الإرجاع أو عمل commit إضافي أو تجاهل الاستثناء.
