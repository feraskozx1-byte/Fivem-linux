# تجارب فعلية معزولة على Proton-CachyOS

نفذت التجارب في 5 نوفمبر 2026 بواسطة `run-loader-probe.py`، عبر UMU المضمّن في Heroic وruntime steamrt4، باستخدام runner الملف الثاني نفسه: `cachyos-11.0-20261015-slr`.

الـprefix جديد تماماً تحت `private/api-probe-cachyos/prefix`، دون نسخ حسابات أو cookies أو جلسات Rockstar. الشبكة مغلقة بواسطة `flatpak --unshare=network`. مُنح مجلد Run-Adhesive-Test وصولاً للقراءة فقط داخل sandbox. لم يُشغل FiveM أو GTA، ولم تُستدعَ `EarlyMode_Init` أو `WineCompat_InstallHooks` أو `CreateComponent`، ولم تُغير هوية Wine أو تذاكر السيرفر. تبقى كل prefixes والنتائج محفوظة.

## API الحقيقي، دون تحميل أي DLL للعبة

`loader-probe.exe`، وضع ABI، داخل بيئة Proton الفعلية:

- `RtlImageDirectoryEntryToData` و`RtlLookupFunctionTable` أعادتا العنوان نفسه لجدول probe.
- حجم الجدول **72 بايت** = ستة إدخالات `RUNTIME_FUNCTION`، وطول lookup المعاد **72**، وليس 6.
- `RtlLookupFunctionEntry` أعادت إدخالاً صالحاً داخل الجدول وbase الصحيح.
- **صفر استثناءات، PROBE_EXIT_CODE=0**.

هذا تحقق API حي يؤيد ABI وحجم الجدول. لا يتضمن بناء CoreRT أو اختباره.

## اعتراض مسار SEH في عملية الاختبار فقط

`seh-hook-probe.exe` لا يستورد أو يحمّل أي DLL للعبة أو الحماية. بعد مطابقة أول 15 بايت من دالة directory في ntdll الفعلية مطابقة دقيقة، أنشأ trampoline مؤقتاً في ذاكرة العملية، ووضع اعتراضاً مؤقتاً يعيد **نسخة مختلفة العنوان** من جدول probe الصحيح، بنفس حدود التخصيص التي يستخدمها إصلاح المصدر. لم يتغير أي ملف ntdll على القرص.

**النتائج الفعلية:**

- القراءة المباشرة و`RtlLookupFunctionTable` و`RtlLookupFunctionEntry` المدمجة فعلياً داخل CachyOS استخدمت النسخة الجديدة عند العنوان `0x6c0000` بدلاً من الجدول الأصلي `0x140005000`.
- إدخال lookup جاء من النسخة الجديدة `0x6c000c` وبقي image base هو `0x140000000` والحجم 72 بايت.
- ثلاث حالات تمرير خارج نطاق override أعادت النتائج نفسها قبل الاعتراض وبعده.
- استُعيدت أول 15 بايت والحماية الأصلية، ثم نجح التحقق من عودة lookup إلى الجدول والإدخال الأصليين.
- **PROBE_EXIT_CODE=0**؛ نتيجة `STRATEGY_RESULT` و`RESTORE_RESULT` و`POST_RESTORE_RESULT` تثبت مراحل التجربة.

**الحدود:** هذا اختبار حي لاستراتيجية الاعتراض وتكامل lookup، باستخدام trampoline تشخيصي محدد لهذه المكتبة فقط. لم يستخدم MinHook، ولم يشغّل CoreRT المبني من التعديلات، ولم يختبر فك stack أو معالجة استثناء حقيقي داخل اللعبة. لذلك ما زال بناء CitiCore واختبار MinHook والعميل مطلوباً.

## تحميل Adhesive خارج FiveM

**الضابط الأول: التحميل المباشر دون تهيئة CoreRT.** ظهر 998 بسبب كتابة إلى `0x60` في `net-tcp-server.dll+0x12db`. تطابق PDB أثبت أنها تهيئة `UvLoopManager` التي تستخدم global instance registry قبل تهيئته. هذا عيب في سياق الاختبار الناقص، لا دليل على عيب جديد داخل هذا المكون في المضيف الصحيح. المصدر الحقيقي للـlauncher يحمل CoreRT قبل المكونات؛ لم يُجر أي patch لإخفاء هذا الخطأ.

**التجربة الأقرب لسياق التحميل:** الوضع `--adhesive-initialized` حمّل CoreRT صراحة أولاً، دون استدعاء EarlyMode أو وظائف إخفاء Wine. نجح التحميل بلا استثناءات، ثم اختُبر تحميل DLL الرسمي نفسه، مع dependency search path الطبيعي.

- CoreRT: handle صالح، خطأ 0، عدد استثناءات 0.
- Adhesive: فشل `LoadLibraryExW` بالرمز **998**، مع استثناء قراءة واحد **0xC0000005**.
- التعليمة الفاشلة داخل **adhesive.dll+0xD9FEC5**؛ هدف القراءة **0xA5D36A**.
- تتبع loader يثبت وقوعها أثناء `PROCESS_ATTACH`/تهيئة CRT الثابتة. stack يتضمن `_initterm+0x2A` في ucrtbase. لم يثبت أنها TLS callback أو API مفقودة.
- معالج VEH سجل الاستثناء ثم أعاد `CONTINUE_SEARCH` دائماً؛ loader تعامل مع الفشل بالطريقة الأصلية. **PROBE_EXIT_CODE=10**، أي فشل التحميل المقصود في ترميز الأداة.

**ما أثبتته التجربة وما بقي:** أصبح لدينا موضع استثناء داخل التهيئة الرسمية في سياق معزول واضح؛ لم يعد تفسير هذه التجربة مقتصراً على غياب import أو خطأ static initializer في dependency. لكنها ليست مضيف FiveM كاملاً ولا تثبت أن عطل العميل السابق ينشأ عند التعليمة نفسها. يبقى السبب الدلالي للقراءة غير الصالحة مجهولاً؛ لا دليل يبرر تصحيح أو تجاوز حماية أو تزوير بيئة النظام. يلزم تتبع من عميل مبني/مصرح به، أو تشخيص من Cfx، للربط النهائي. إعادة بناء CoreRT لا تعيد بناء Adhesive ولا تضمن صدور cfxTicket2.

## النتائج والخصوصية وإعادة التنفيذ

`live-probe-results.txt` يجمع النتائج المنقحة التي كتبها برنامجا الاختبار مباشرة إلى ملفات داخل C: المعزول. السجلات الخام وملخصات كل تشغيل تحت private بصلاحيات مجلد 700. لا ينبغي رفعها تلقائياً. probe يستخدم `CREATE_NEW` حتى لا يستبدل نتيجة سابقة؛ أي إعادة تجربة تحتاج اسماً/نسخة prefix جديدة مع الاحتفاظ بالقياسات السابقة.

أول تشغيل v1 لم يُظهر stdout بسبب مسار `umu.exe` الذي لا يورث المقابض ويفصل console. لذلك لم يُعتبر exit code للغلاف دليلاً على نجاح البرنامج. v2/v3 يكتبان نتائج مباشرة مع `PROBE_EXIT_CODE` ويتحقق الغلاف من وجود الملف. نتائج هذا التقرير تعتمد على تلك الملفات، لا على نجاح UMU وحده.

أدوات البناء المصغرة: clang لاستهداف x64 Windows، وlld-link وllvm-dlltool؛ لا CRT ولا Windows SDK مطلوبان لهذين برنامجي التشخيص الصغيرين فقط. **لا تعني هذه الطريقة إمكان بناء CoreRT الكامل دون Visual Studio/SDK واعتمادياته.** ملفات C وسكربتا البناء موجودة بجوار هذا التقرير. التجارب لا تستبدل أي DLL مستخدم في مجلدي التشغيل.
